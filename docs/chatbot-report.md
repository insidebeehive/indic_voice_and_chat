# The ChatBot Module: Architecture, Design Rationale, and Evaluation

## Abstract

This chapter documents the design and implementation of the ChatBot module, the text-based, retrieval-augmented customer-support agent within the platform. The ChatBot is the inbound counterpart to the platform's outbound VoiceBot: where VoiceBot places calls to leads, ChatBot receives customer conversations over text and images, grounding its answers in tenant-specific knowledge via retrieval-augmented generation (RAG), executing CRM tool calls on the customer's behalf, and escalating to a human operator or a live voice call when appropriate. The module is built as a single agent class (`ChatBotAgent`) sitting atop a hybrid dense/sparse retrieval pipeline, a deterministic hallucination guard, an agentic tool-calling loop, and a purpose-built natural-language classifier for a genuinely difficult sub-problem: distinguishing English from romanized (Hinglish) Hindi in a code-mixed, multilingual customer base. This last subsystem is examined in detail as a case study, since its development history — four regression-driven revisions across five weeks — offers a concrete illustration of an iterative, evidence-driven design process rather than a specification arrived at correctly on the first attempt.

## 1. Introduction and Scope

### 1.1 Problem Statement

Customer support for an online gaming/betting platform must answer questions spanning account status, KYC verification, wallet operations, game rules, bonus terms, and responsible-gaming guidance — for a customer base that communicates in English, Hindi (in both Devanagari script and its Roman-script "Hinglish" transliteration), and several other Indic languages, often switching between them mid-conversation. A rule-based or purely retrieval-only system cannot synthesize an answer that combines platform documentation, live account data from a backend CRM, and natural conversational language; a purely generative system risks fabricating account-specific facts (balances, transaction IDs) that must never be invented. The ChatBot module is the platform's answer to this: a retrieval-grounded, tool-using conversational agent with an explicit, code-enforced rule against inventing player-specific data.

### 1.2 Position in the Broader System

The platform documentation (`docs/chatbot.md`) frames the relationship between the two conversational subsystems precisely: *"VoiceBot = outbound (we call leads); ChatBot = inbound (customers chat with us)."* ChatBot is deployed per tenant, with each tenant's own CRM building its own front-end UI against a shared API contract (a reference implementation exists at `/chat-widget`). The module was scoped and delivered incrementally — text and RAG first, then agentic tool-calling, then CRM integration, multimodal (image) support, an escalation webhook, and finally a handoff mechanism into a live voice call — corresponding to a sequence of merged pull requests over the module's development.

An earlier planning document, `docs/chatbot-requirements.md`, is retained in the repository in its pre-build "draft / not scheduled" state and is useful chiefly as a record of the original motivation and of what was deliberately descoped. That document's stated motivation was a competitive gap analysis against an existing admin panel used for manual chat responses, whose principal weakness was identified as having "no AI/RAG — auto-responses are static/rule-based." Retrieval-augmented generation was accordingly treated as the ChatBot module's core differentiator rather than an optional enhancement. The same document explicitly deferred a full ticketing system, agent-presence indicators, a dedicated mobile application, and full role-based access control — scope that remains, to date, unimplemented and is revisited in §8.

## 2. System Architecture

### 2.1 The Agent Class and Its Two Execution Modes

The module's entry point is `ChatBotAgent` (`src/agents/chatbot.py`), constructed with an LLM provider, a hybrid retriever, an optional CRM-specific retriever, a set of CRM tool definitions and an executor callback, a session store, and a small set of configuration values — among them `max_context_chars` (the retrieval budget injected into the prompt, default 2000 characters), `enable_tools` (whether the agentic tool-calling loop is active), and `max_tool_rounds` (a hard cap of 2, preventing an unbounded tool-calling loop). Two retrievers are composed in a fixed order — a shared, CRM-wide knowledge base first, then the tenant-specific knowledge base second — so that a query can draw on both general platform knowledge and tenant-specific content, with the tenant's own material taking precedence in any conflict during response synthesis.

Every user turn passes through a single public method, `handle_message`, which short-circuits immediately on empty or whitespace-only input (returning a structured `parse_error` rather than invoking the LLM), and otherwise dispatches to one of two internal execution paths:

- **`_single_shot`** performs retrieval, assembles the system prompt, and issues exactly one LLM call constrained to a structured JSON response format, then applies the hallucination guard and persists the turn. This is the simpler of the two paths and is used when tool-calling is disabled.
- **`_handle_with_tools`** is the path used in production (confirmed by the deployment factory's `enable_tools=True`). It runs an agentic loop of up to two rounds, in which the LLM is called in **plain-text** response mode rather than structured JSON — a deliberate accommodation of the observation that JSON-constrained output and native tool-calling are, for at least one supported provider (Gemini), mutually incompatible in this SDK. Within each round the model may issue zero or more tool calls (knowledge-base search, CRM lookups, escalation, or a voice-call offer); results are executed and fed back into the conversation, and the loop terminates either when the model produces a final answer without further tool calls, or after the round limit is reached, at which point one final plain-text-only call is forced to guarantee the customer always receives a reply rather than a silent failure.

This two-path design reflects a common pattern in agent architectures generally: a simple, structured-output path suffices for a single retrieval-and-answer turn, while a tool-using agent requires an unstructured, multi-round conversational loop because the model's own tool-calling protocol occupies the response channel that would otherwise carry the structured envelope.

### 2.2 Session and Context Management

The system prompt is rebuilt from scratch on every turn (rather than cached across a conversation), which lets per-turn language directives and freshly-retrieved context be injected precisely where needed, but at a computational cost that scales with however much conversation history is replayed to the model. To bound this cost, only the most recent ten exchanges are replayed into the prompt on any given turn, even though the full transcript is retained in the session object for user-interface and audit purposes. Without this bound, the message list sent to the LLM would grow by roughly two entries per turn indefinitely, degrading both latency and per-turn token cost as a conversation lengthens — a straightforward but necessary engineering trade-off between conversational memory and runtime cost.

Turn persistence writes both the user and assistant turns to the session's Redis-backed store, and separately tracks a `turn_count` computed as the number of turns with a `user` role — a small counting idiom that recurs, not coincidentally, in the language-detection subsystem discussed in §4.3, where the identical test ("has this session ever seen a user turn before") determines whether the current message is the conversation's opening message.

### 2.3 Hallucination Mitigation

Because the platform's one inviolable constraint is that the model must never invent player-specific figures, the ChatBot module implements a dedicated post-processing guard (`apply_hallucination_guard`, `src/rag/context_builder.py`) applied after every retrieval-grounded LLM response, comprising three independent checks:

1. **Citation validation.** Any source the model claims to have used (`sources_used`) that does not correspond to an actual retrieved chunk is stripped from the response, and the response's self-reported confidence is downgraded to `"low"` — treating an invented citation as presumptive evidence that the surrounding content may also be unreliable.
2. **Zero-retrieval override.** If the retrieval step returned no chunks at all, the guard discards whatever the model produced and substitutes a fixed, language-appropriate fallback message, forcing `confidence="low"` regardless of what the model reported — on the reasoning that a model given no grounding material has no legitimate basis for a confident, specific answer.
3. **Silent-hallucination detection.** Even when retrieval succeeded, a response reporting high confidence with zero citations is treated as a likely hallucination and is substituted with the same fallback — the inference being that a genuinely well-grounded answer should be able to point to at least one of the chunks it drew from.

The guard is deliberately skipped for turns where no retrieval was attempted at all — a plain greeting, an image-only turn, or a turn resolved entirely by a CRM tool call — since such turns are, in the module's own terms, "legitimately ungrounded" rather than failures of grounding.

## 3. Retrieval-Augmented Generation Pipeline

Retrieval is implemented as a hybrid dense-and-sparse search (`HybridRetriever`, `src/rag/retriever.py`), combining a FAISS-backed dense vector index with a BM25 sparse lexical index, run concurrently for each query and then fused via independently min-max-normalized, weighted scores (a default 70/30 split favoring the dense signal). The fused candidate set is optionally passed through a cross-encoder reranker before being trimmed to the final top-k results returned to the calling agent, with results below a configurable similarity floor discarded outright. This hybrid design is a standard and well-motivated choice for retrieval over short, often terminology-heavy support documents: dense embeddings capture semantic similarity that a literal keyword match would miss, while the sparse BM25 component recovers exact terminology matches (product names, specific error codes) that a dense embedding can sometimes under-weight.

Two embedding backends are supported: a local `sentence-transformers` model (multilingual, avoiding a dependency on any external API for this stage of the pipeline) and a Gemini-hosted embedding API, the latter chosen specifically to avoid bundling a torch/sentence-transformers dependency into the deployment image, at the cost of an external API call per embedding. Because Gemini's embedding API does not L2-normalize its output at reduced dimensionality, the adapter normalizes manually before insertion into a FAISS index built for inner-product similarity — a detail that, if missed, would silently degrade retrieval quality without raising any visible error, since cosine similarity computed against un-normalized vectors is not equivalent to the correct inner product over the intended unit-normalized space.

The BM25 half of the index is maintained lazily: any insertion or deletion invalidates a cached index object rather than triggering an immediate, potentially expensive rebuild, deferring the rebuild cost to the next query. Vector storage itself is provider-abstracted (FAISS for a per-tenant on-disk index in the reference deployment, with a PostgreSQL/pgvector adapter also available as a config-driven alternative), consistent with the platform's general pattern of treating storage and inference backends as swappable providers behind a common interface rather than hard-coded dependencies.

## 4. Prompt Engineering and the Language-Detection Subsystem

### 4.1 System Prompt Structure

The system prompt is assembled section-by-section and joined in a fixed order: the current date, an identity block, a scope-and-guardrails block, retrieved RAG context (when present), tool-use instructions, escalation instructions, a "resolved" closing-condition instruction, a language-handling block, response-quality guidance, and finally the required JSON response schema. A final "additional directives" section — carrying the per-turn language-detection result described below — is appended last, on the principle that instruction position affects a language model's weighting of competing directives, and the per-turn, most-current instruction should take precedence over the more general guidance that precedes it.

The identity block encodes the module's one non-negotiable constraint in explicit terms: the model must never invent player-specific figures — account balances, transaction identifiers, banking details, bonus amounts — while being otherwise encouraged to answer generously and directly from its own general knowledge (game rules, responsible-gaming guidance, how betting mechanics work) rather than withholding help merely because no CRM tool happened to return that information. This is a deliberately asymmetric guardrail: broad license to help, paired with a narrow, absolute prohibition on a specific, well-defined category of fabrication. The same block instructs the model to keep implementation details — file names, tool identifiers, internal endpoint paths, environment labels, internal identifiers surfaced in tool responses — out of any customer-facing reply, a standard defensive measure against a support agent inadvertently leaking internal system structure to an end user.

The scope block is conditioned on whether the tenant has CRM tools configured: with tools available, the model is instructed to invoke the relevant tool immediately for account-specific queries and to present whatever the tool returns without truncation or paraphrase of numeric fields; without tools, the model is instead instructed to redirect the customer to the platform's own account interface rather than attempting to answer from memory. A further, narrowly-scoped rule governs withdrawal-status queries specifically, encoding a four-state business rule (submitted, approved and within a 48-hour window, approved and past that window, or rejected) that the model evaluates against the current date and the tool-reported approval timestamp — an example of business logic expressed as a natural-language instruction rather than as code, a pattern which trades implementation simplicity for a dependency on the model correctly interpreting and applying the rule on every turn.

### 4.2 The Language-Detection Problem

A recurring design challenge in this module is that **script is not language**. Romanized Hindi ("mera balance kya hai") is written in the Latin alphabet and is, at the character level, indistinguishable from English; conversely, a customer typing in Devanagari script is unambiguously writing Hindi. The module's language-handling logic is built around this asymmetry: a dedicated script-detection function (`_detect_script`) reliably identifies text written in a native Indic script (Devanagari, Bengali, Gujarati, and several others, via Unicode code-point range membership, requiring at least 60% of a message's alphabetic characters to fall within a single script's range), but deliberately returns no result for predominantly Latin-script text — the function's own documentation is explicit that this is not an oversight but a considered decision, since treating all Latin-script text as English would misclassify every Hinglish message.

A second function, `_latin_language_hint`, handles the harder case of classifying Latin-script text that `_detect_script` has, by design, left unresolved. It applies a curated list of forty common romanized-Hindi words (chosen specifically to exclude terms that collide with genuine English words, such as "do" or "the," to avoid false-positive Hinglish classification) and, failing a marker match, falls back to a simple length heuristic: three or more marker-free words are classified as English, while one or two marker-free words are left unclassified, on the reasoning that a short message such as "ok" or "thanks" carries too little signal to justify overriding whatever language the conversation has already established.

### 4.3 Case Study: An Iterative, Regression-Driven Design History

The language-detection subsystem's present form is the product of four successive corrections, each addressing a genuine failure mode introduced by the correction before it — a instructive record of how a seemingly simple classification problem (which language is this message in?) resisted a correct solution on the first three attempts, and was only resolved by a deterministic, marker-based classifier explicitly designed to defeat a specific failure mode of its predecessor.

| Date | Commit | Change | Failure addressed | New failure introduced |
|---|---|---|---|---|
| 2026-06-22 | `8f1e34c` | Server-side script detection with a per-turn injected language directive | Unreliable LLM-internal language judgment when retrieved context was itself in Hindi | All-Latin text classified as "English," forcing romanized Hindi into English replies |
| 2026-07-15 (00:06) | `b6d3f1e` | Latin-script text reclassified to "no signal" rather than "English" | The above (Hinglish forced into English) | A message with no signal fell through to the tenant's configured default language, so a Hindi-default tenant answered plain English text in Devanagari |
| 2026-07-15 (11:04) | `dd3e3e4` | An advisory instruction letting the model choose Hinglish or English itself for ambiguous Latin text | The above (plain English answered in Devanagari) | The advisory was too weak against conversational momentum: a chat that had been running in Hinglish continued answering plainly-English messages in Hinglish |
| 2026-07-15 (21:44) | `6758d39` | A deterministic, marker-based classifier producing a firm directive that explicitly overrides prior turns' language | The above (Hinglish momentum overriding a clear English message) | (Narrowed, latent) very short Latin-script messages still resolved to "no signal," inheriting the second failure mode in miniature |
| 2026-07-28 | `8ffcbd6` | An opening-message-only default to Hinglish when no signal exists at all | A single ambiguous opening word (e.g. "games") defaulting to the tenant's configured language, which could be Devanagari Hindi even for an English-speaking customer | — (deliberately scoped to be unreachable once any prior user turn exists, to avoid reopening the third failure mode) |

Three of these five commits were made within a single 21-hour span on 15 July, each one a direct, tested response to a regression the previous commit had introduced — evidence of a design problem that was not, and arguably could not have been, correctly specified in advance, since the correct behavior depends on an inherent ambiguity in the input (a short, script-ambiguous message genuinely does not, on its own, disambiguate between two plausible interpretations) rather than on an implementation defect. Each of the four corrective commits shipped together with new or revised regression tests in the same change, so that the specific failure it fixed is now guarded against by an automated test rather than only by the accompanying prose explanation.

The most recent revision (28 July) illustrates a further refinement of engineering discipline visible across this history: rather than broadening the Hinglish default to cover every ambiguous turn — which would have been the simpler change but would have reintroduced the third failure mode (Hinglish momentum overriding an established English conversation) — the fix was deliberately scoped to be reachable only for a session's literal first message, verified by checking whether any prior turn in the session carries a user role. This scoping decision was independently confirmed, during the change's review, to make the new code path structurally unreachable once a single user turn exists in the session, directly addressing the specific risk the design needed to avoid rather than merely avoiding it by convention.

## 5. Tool-Calling and CRM Integration

Three tools are available to the agent unconditionally: a knowledge-base search tool (querying the same hybrid retrieval pipeline described in §3), an escalate-to-human tool requiring a reason and a summary, and an offer-a-voice-call tool that explicitly instructs the model not to request a phone number from the customer (since the voice handoff, described in §6, operates over the customer's existing browser session rather than a telephone number). Beyond these three, each tenant may register its own CRM-specific tools, appended to the available tool set at runtime; a tenant with no tools of its own falls back to a shared catalog associated with its linked CRM entity, with a defined precedence order (a tenant's own tools first, the shared CRM catalog second) and per-tenant credential resolution even when a shared-catalog tool is used, so that no tenant's requests are authenticated with another tenant's credentials.

Tool execution is defensively wrapped throughout: a failing knowledge-base search degrades to an empty result set with an error notation rather than terminating the turn; a failing or unconfigured CRM tool call degrades to a generic "not yet connected" holding message rather than propagating an exception to the customer. This consistent choice — degrade gracefully rather than fail the turn — reflects a design priority appropriate to a customer-facing system, where an unhandled exception mid-conversation is a materially worse outcome than an honest, if unhelpful, holding message.

## 6. Escalation, Multimodal Input, and Chat-to-Voice Handoff

When a conversation is escalated — either by explicit tool call or by the customer's own request — a webhook notifies the tenant's backoffice system of the event, carrying whatever claim and agent-connection URLs a human operator needs to pick up the conversation. The webhook payload is HMAC-signed when a signing secret is configured for the tenant; when none is configured, the payload is still sent, unsigned, accompanied by a warning logged on the platform's own side — a fail-open design that prioritizes uninterrupted delivery of escalation events over strict security, on the judgment that a missed escalation (should the platform instead fail closed) is a worse operational outcome than an unsigned payload to a tenant who has not yet configured a signing secret.

A separate integration point exists for tenants using Chatwoot as their backoffice inbox: inbound Chatwoot webhook events resolve their target tenant purely from an inbox identifier embedded in the payload, without any bearer-token authentication on that specific endpoint — a deliberate, accepted characteristic of this integration path rather than an oversight, and one worth stating plainly here as a known property of the system rather than leaving it undocumented.

Multimodal input is supported for images natively, passed through to the underlying model as inline image data alongside the customer's text; video is handled on a best-effort basis, extracting a small number of representative frames when the necessary decoding library is available, and degrading to a plain text placeholder rather than blocking the reply when it is not. Retrieval, notably, is run only against the caption or accompanying text of a multimodal turn, not against the media itself — a scope limitation consistent with the retrieval pipeline's text-only design (§3).

Finally, a conversation that reaches a point where a live voice call would serve the customer better than continued text can be handed off directly: the platform summarizes the chat transcript into a short context note, stores it under a short-lived token, and opens a browser-based voice session that starts already primed with that context — allowing a customer to move from typing to speaking without repeating what they have already explained. This handoff path is wired unconditionally at platform startup, independent of whether the administrative developer console is enabled, since it is a customer-facing production feature rather than a development tool.

## 7. Testing and Validation

### 7.1 Unit Test Coverage

The module's automated test suite exercises both the conversational happy path (a full retrieval-grounded answer with correct citations) and its edge cases: empty input handling, the hallucination guard's citation-stripping behavior, session history replay across a multi-turn conversation, in-memory degradation when no persistent store is configured, and — reflecting the case study in §4.3 — a specific regression test for every documented failure mode of the language-detection subsystem, including a test that seeds a real prior conversational turn (rather than manipulating internal state directly) specifically to distinguish a mid-conversation short acknowledgment from a session's genuine opening message.

### 7.2 Load Testing

A dedicated load-testing script exercises the module's session-creation, WebSocket-connection, and first-reply-latency path under concurrent load from a configurable number of simulated customers, with session starts spread over a ramp window rather than issued simultaneously, reporting per-stage success counts and percentile latencies. This script exists specifically to give the engineering team the ability to reproduce, on demand, a stress scenario previously identified only informally by an external stakeholder's own testing — a useful instance of converting an ad hoc, externally-reported concern into a repeatable, owned test.

## 8. Known Limitations and Future Work

- One existing unit test, asserting that the system prompt contains specific "operator-specific" guardrail language, currently fails against the present prompt wording; investigation confirms this is a stale test assertion left behind by an otherwise-legitimate prompt rewrite, rather than a missing guardrail in the deployed prompt itself, and the appropriate remedy is a test update rather than a prompt change.
- The Chatwoot inbound webhook's lack of per-request authentication (§6) is a deliberate, accepted trade-off for that specific integration rather than an unaddressed gap, and is noted here for completeness rather than as an outstanding defect.
- The original planning document's deferred scope — a full ticketing system, agent-presence indicators, a dedicated mobile client, and comprehensive role-based access control — remains unimplemented, consistent with that document's own explicit "out of scope" designation rather than representing incomplete delivery against the module's actual design goals.
- A widely-cited internal figure describing successful load-test throughput ("200 of 200 sessions") could not be independently re-confirmed against a specific test run during the preparation of this chapter and should be treated as provisional pending a fresh, logged run of the load-testing script described in §7.2.

## 9. Conclusion

The ChatBot module demonstrates a retrieval-grounded, tool-using conversational agent architecture built around one central, non-negotiable constraint — that account-specific data must never be fabricated — enforced not only through prompt instruction but through an independent, code-level post-processing guard that does not rely on the model's own self-reported confidence. Its most instructive engineering property, however, is not any single design decision but the visible history of one: the language-detection subsystem's four-revision correction sequence is a concrete record of a problem whose correct solution depended on discovering, through real regressions, exactly which failure modes a plausible-seeming fix could reintroduce — and of a final design that succeeded specifically because it was scoped narrowly enough to be provably incapable of reopening the failure mode its predecessor had already fixed.
